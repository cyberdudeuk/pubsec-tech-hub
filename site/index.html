    What this hub does not claim

    A listing is not an endorsement, an assurance or a procurement route. Facts come from the owners' own publications, with the date and source beside each one. "Not declared" means the owner has not said, not that the answer is bad.

    Why there are no stars

    Mobile stores rank apps by ratings and reviews. Here anyone could invent them and nobody could check them, so the hub shows only facts with sources: what it is, who owns it, how mature the owner says it is, its licence, and who declares they use it.

    List, claim or declare use

    Contact is by form only. Every form is a public GitHub issue, so don't include personal details.

    List a product

    1. Add a publiccode.yml file to the root of the product's public repository. It is a short metadata file; the standard explains each field and Developers Italia's guide shows a worked example.
    2. Submit the listing form with the repository address. Open the listing form.
    3. Moderation: the editor checks that the body is a public body and the repository is real, then adds it to the weekly harvest, normally within 7 days.
    4. Weekly harvest reads the file every Monday, so changes you make to it appear within a week.

    Claim a curated listing

    If a listing here describes your product, claim it. Once your repository has a publiccode.yml file the curated text is replaced by your own.

    Declare that your body uses a product

    Use shows only when a body says so itself. Declare use with your body's name and, if you can, a public page that mentions it.

    What moderation checks

    • The owner is a UK public body, or a supplier publishing on its behalf.
    • The repository and live service addresses work.
    • Facts that are not in publiccode.yml carry a public source.
    • Nothing personal: contact details in publiccode.yml are never shown here.

      Open data

      Everything on this site is in open JSON files you can harvest, under CC BY 4.0.

      • data/hub.json: listings, sources, glossary, requirements
      • data/harvested.json: the latest harvest from publiccode.yml files
      • data/reconciliation.json: the Figma prototype reconciliation register

      The listing fields are explained in the data dictionary.

      How the harvest works

      1. Every Monday a free GitHub Actions job reads the repositories on the harvest list.
      2. It fetches each publiccode.yml file and keeps only the fields the hub shows: name, description, maturity, licence, platforms, categories, the live address and the owner.
      3. It removes every contact detail and email address before saving.
      4. It runs the same checks as every release, then republishes the site. If a check fails, nothing is published and an issue is opened.

        Theory of change

        1. Problem: public bodies rebuild things other bodies already run, because finding them means reading many blogs and repositories.
        2. Activity: one directory, harvested from the owners' own metadata, with sources on every fact.
        3. Output: listings anyone can filter, search, cite and harvest.
        4. Outcome: teams check the hub before they build, and owners keep their publiccode.yml current.
        5. Assumption to test: owners will add publiccode.yml. Today none of the twelve UK repositories listed here has one, so the hub starts curated and says so.

        Architecture

        • One self-contained page, built from JSON by tools/build.py; no server, no cookies, no tracking.
        • Free GitHub Actions only, every action pinned to a commit.
        • Decision: no ratings or reviews (they cannot be verified). Decision: link to existing directories rather than copy them.

        About

        Effort to keep it running

        About 30 to 60 minutes a week for one person (estimate): read new issue forms, add accepted repositories to the harvest list, and glance at the weekly run. A monthly link check opens an issue only when a link breaks. Running cost: nothing; it uses free GitHub Pages and Actions on a public repository.

        Method

        Facts come from owners' own publications, read on the evidence date shown. Licences come from the licence file in each repository. Maturity is shown only when an owner declares it. Anything the editor could not check is left out rather than estimated.

        The case against this hub

        • "Another directory nobody updates." The base rate for government catalogues going stale is high. Answer: the hub reads owners' own files weekly, links to directories that already exist, and shows its harvest date on the page.
        • "Twelve listings is not a store." True today. Answer: the first listings are the best-evidenced common platforms; growth depends on owners adding publiccode.yml, which none of the twelve has yet. That is the hub's main risk, stated here first.
        • "Usage figures are owners marketing themselves." Partly. Answer: they are labelled with their source and date, and the hub shows declared users separately.
        • "It duplicates the API catalogue or the NHS login directory." Answer: it links to them instead of copying them.
